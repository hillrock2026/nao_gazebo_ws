# Phase A：NAO Gazebo 数据采集最小闭环

## Qoder Implementation Task

你现在负责在现有 `nao_gazebo_ws` 工程上实施：

> **Phase A：冻结“数据采集最小闭环”**

本阶段的唯一目标是建立一个可靠、可重复、可审计的最小 Episode 数据生产闭环：

```text
Frozen gait parameters + seed
        ↓
Gazebo / ROS
        ↓
NAO gait execution
        ↓
raw trajectory collection
        ↓
atomic episode publication
        ↓
manifest + provenance
        ↓
Episode Integrity validation
```

本阶段不是 gait optimization。

本阶段不是 Stage 7 contract validation。

本阶段不是修改 P1-R v3。

本阶段不是设计新的 gait algorithm。

# 3. Phase A 的明确边界

## 本阶段必须完成

### A1. 一个固定 gait 可以启动

给定：

```text
gait parameters θ
seed
episode_id
duration
```

能够启动 Gazebo + NAO gait producer。

---

### A2. 一个 Episode 可以完整采集

至少确保：

```text
simulation clock
joint states
joint commands
IMU
left contact
right contact
body pose
```

能够进入 episode 数据。

---

### A3. Episode 必须原子发布

不得出现：

```text
半写入 episode 被误认为完整 episode
```

应该采用类似：

```text
episode.tmp/
    ↓
validation
    ↓
atomic rename
    ↓
episode/
```

如果现有 Phase 4D 已经正确实现，则直接复用。

---

### A4. 生成 provenance

每个 episode 至少能够回答：

```text
这个数据是谁产生的？
什么时候产生的？
使用什么 seed？
使用什么 gait parameters？
使用什么 Gazebo/world/physics？
使用什么代码版本？
实际运行了多久？
数据是否完整？
```

---

### A5. 自动 Episode Integrity 判定

本阶段只建立：

```text
episode_integrity
```

不要把它和：

```text
contract_status
```

混在一起。

例如：

```json
{
  "episode_integrity": "PASS"
}
```

或者：

```json
{
  "episode_integrity": "FAIL"
}
```

---

# 4. 三种状态必须严格分离

后续系统会有：

```text
episode_integrity
measurement_quality
contract_status
```

Phase A 只负责第一项：

```text
episode_integrity
```

可以为未来字段预留位置，但：

> 不要在本阶段实现新的 P1-R contract logic。

特别禁止把：

```text
lateral_ratio > 0.50
yaw_change > 30°
```

之类 Stage 7 contract gate 塞进 Episode Integrity。

一个 gait 完整运行但 gait quality 不好：

```text
episode_integrity = PASS
contract_status = FAIL
```

这是允许的，而且是后续 gait dataset 必须支持的。

# 7. Provenance 最低信息要求

至少保存：

```text

seed

gait parameters

```

尤其注意：

> **实际执行的 command 必须来自真实执行路径，而不是仅仅保存“理论 command”。**

历史 Stage 7 曾经出现过：

```text

```

导致一个看起来通过很多 gate 的 attempt 最终无法作为有效实验。

Phase A 必须避免这个问题。

# 13. 不要把“机器人摔倒”自动判为 Episode Integrity FAIL

这是非常重要的设计原则。

例如：

```text
NAO 正常运行 8 秒
然后摔倒
```

如果所有原始数据完整：

```text
episode_integrity = PASS
```

同时以后可以有：

```text
fall_detected = true
```

或者：

```text
measurement_quality = VALID
```

原因：

> 对 gait optimization 来说，“摔倒的 gait”是非常有价值的数据。

它不是坏数据。

真正应该判 FAIL 的是：

```text
数据损坏
数据缺失
时间轴损坏
collector failure
Gazebo crash
schema corruption
```

---

# 14. 必须区分三类失败

最终至少区分：

## Infrastructure failure

例如：

```text
Gazebo failed to start
ROS failed
collector crashed
process failed
```

## Data integrity failure

例如：

```text
timestamps corrupted
samples incomplete
schema invalid
missing signals
```

## Gait outcome

例如：

```text
fall
large yaw
large lateral drift
poor clearance
```

第三类不是 Episode Integrity failure。

请始终记住：

> Phase A 不是证明 NAO gait 是好的。

它只证明：

> **我们已经拥有一条可靠的数据生产管线，可以把一次 NAO Gazebo gait execution 转换成一个可追溯、可验证的 Episode。**

如果现有工程已经满足某项要求：

> 不要为了“留下代码修改痕迹”而修改它。

优先：

```text
reuse > minimal fix > new implementation
```

完成后停止，不要自行进入 Phase B。
